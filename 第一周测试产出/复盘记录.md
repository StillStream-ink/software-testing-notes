# SauceDemo 登录测试复盘记录

> 记录从第一版（16条）到第二版（33条）的完整迭代过程


## 一、背景

第一周使用 AI 辅助生成了 16 条 SauceDemo 登录测试用例，当时觉得“差不多了”就直接执行并报了 Bug。最近重新审视这份用例，发现存在**测试数据模糊、预期结果不确定、安全覆盖不足**等问题，于是进行了全面重构，扩展到 33 条。

这份复盘记录整理了两次设计的差异和关键认知变化。


## 二、核心变化对比

| 对比项 | 第一版（16条） | 第二版（33条） |
|--------|---------------|---------------|
| 用例总数 | 16条 | 33条 |
| 测试方法标注 | 无 | 等价类/边界值/场景法/安全测试 明确标注 |
| 安全测试覆盖 | 2条 | 9条 |
| UI交互测试 | 无 | 4条 |
| 测试数据精确度 | 部分模糊 | 全部量化 |
| 预期结果确定性 | 部分写"或" | 全部确定 |
| Bug判断方式 | 发现异常直接报 Bug | 先确认系统设计，再决定结论 |


## 三、关键改进点

### 改进 1：测试数据从模糊变精确

| 版本 | 写法 |
|------|------|
| 第一版 | "输入用户名 standard_user（含前后空格）" |
| 第二版 | "输入用户名 `" standard_user "`（前后各1个空格）" |

**变化**：明确量化，确保任何测试人员都能精确复现。


### 改进 2：预期结果从不确定变确定

| 版本 | 写法 |
|------|------|
| 第一版 | "登录成功，但页面加载明显慢（>2秒），最终进入商品页" |
| 第二版 | "登录成功，加载约3-4秒后进入商品页" |

**变化**：先实际执行，再记录确定结果，消除"或"和"大概"。


### 改进 3：Bug判断方式从直接报改为先确认设计

| 版本 | 做法 |
|------|------|
| 第一版 | 发现用户名带空格登录失败 → 直接报 Bug |
| 第二版 | 确认 SauceDemo 设计不支持 trim → 结论改为"通过" |

**变化**：测试预期应基于需求/设计文档，而非个人假设。


### 改进 4：错误提示从简化版改为完整版

| 版本 | 写法 |
|------|------|
| 第一版 | "Username and password do not match" |
| 第二版 | "Epic sadface: Username and password do not match any user in this service" |

**变化**：完整记录产品前缀，与实际页面严格一致。


## 四、个人收获

1. **测试用例是给别人执行的**：数据必须精确到可复现，不能写"含空格"而不写几个
2. **预期结果必须确定**：不能写"或"，不确定就先去测
3. **报 Bug 前先确认是不是系统设计**：不能把自己的假设当标准
4. **错误提示要完整**：含产品前缀（如 Epic sadface），不能只记后半句
5. **安全测试不能只覆盖 2 条**：SQL注入、XSS、路径遍历、暴力破解、信息泄露都要考虑

## 六、一句话总结

**最大的变化不是"会写的用例变多了"，而是"知道自己哪里会写错了"。**


## 七、学习收获

1. **测试数据必须精确**：“含前后空格”要写成“前后各1个空格”，确保任何测试人员都能精确复现
2. **预期结果不能写“或”**：不确定就去测，测完写确定的结果
3. **发现异常不直接报Bug**：先确认是系统设计还是缺陷，不能把自己的假设当标准
4. **错误提示要完整记录**：包含产品前缀（如 Epic sadface），不能只记后半句
5. **安全测试不能只覆盖2条**：SQL注入、XSS、路径遍历、暴力破解、信息泄露都需要考虑
6. **敢于推翻自己**：第一周报的Bug，后来发现判断有误，敢于修正并说明理由

## 八、Bug 报告修正说明

第一周提交的 Bug 报告中包含一条：
> Bug：用户名含首尾空格时登录失败，提示不匹配

**修正结论**：该问题**不属于系统缺陷**。

**原因**：SauceDemo 的设计逻辑是**不对用户名做 trim 处理**，带空格的用户名被视为完全不同的用户名，登录失败属于**预期行为**，而非系统缺陷。

**处理方式**：
- 原始 Bug 报告已保留（见 `第一周Bug报告.docx`），作为学习过程的真实记录
- 用例 TC-010 的预期结果已修正为“登录失败，显示错误提示”，结论改为“通过”
- 此修正已在用例库 v2.0 版本中落地

**学习收获**：报 Bug 之前，先确认是“系统设计”还是“系统缺陷”，不能把自己的假设当成标准。
